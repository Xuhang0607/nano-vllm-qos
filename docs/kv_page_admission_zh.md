# 优先级感知的 KV 页准入预算

## 为什么继续修改

上一轮静态驻留上限把回收次数从 5 降到 0，却把交互 TTFT P95 从约 305 ms 推高到 4,850 ms。
这些是单次带追踪的诊断观察，不能当作正式性能对比，但足以说明“少抢占”不是唯一目标。
本轮候选改为基于页需求的短期软预留，默认仍关闭。

对照本仓库导入的上游快照 `de7a265`，其调度器按本步批次数和当前分配容量决定 Prefill 准入，
没有这里新增的优先级分组页增长预留与候选跳过机制。它已经支持基本的分块 Prefill，不能把分块本身写成新实现。
`max_num_seqs` 作为每步批次约束不一定是上游错误；本项目是在这一语义之外扩展在线服务的准入目标。
这个对照只针对已导入快照，不表示检查了最新上游版本或生产 vLLM 的全部实现。

## 机制

配置 `kv_admission_lookahead=H`：0 保留原行为，正数表示预测未来最多 H 个 Decode Token 的页增长。
对于同等或更高优先级的运行请求，计算：

```text
新增页 = max(0, ceil((物理已缓存 Token + 待执行 Prefill Token + 未来 Decode Token) / 页大小)
                - 已分配页数)
```

未来 Decode Token 不超过请求剩余输出预算；刚被选中的 Prefill 预计产生一个输出 Token，因此先扣除它。
候选请求自己的后续页增长也被计入预算。对于压缩过的运行请求，使用物理缓存长度，不使用 RoPE 逻辑位置。

准入时先使用现有 `can_allocate` 获取前缀匹配计划，再读取该计划的空闲池分配成本：

```text
当前分配成本 = 候选请求的完整输入页数 - 已被其他请求持有、可以共享的匹配页数
```

空闲池里虽然还有数据的缓存页，再次被持有时也会消耗空闲页名额，不能从成本中扣除。
读取计划不会再次查找前缀，避免重复修改查找计数和 LRU 状态。

如果分配后剩余空闲页少于预留页数，则暂缓该候选。高优先级请求不为低优先级请求预留未来增长空间，仍需通过真实容量检查。
暂缓大请求后，会继续检查其他候选，每步最多暂缓 `max_num_seqs` 个候选，避免无限扫描。
后续候选仍受 PALS 的 Prefill/Decode 阶段比较约束，不是无条件插队。

### 一个取舍示例

假设普通请求已经用满 6 页，每页 256 Token，物理缓存长度为 1,536。
预测它接下来生成 32 个 Token，就需要为它预留第 7 页。
如果新请求也是普通优先级，它需要考虑这一页；如果新请求优先级更高，则可以不为这个普通请求保留增长空间。
因此高优先级请求可能更快准入，但普通请求之后仍可能被抢占。这是显式取舍，不是无条件“无抢占”。

静态驻留上限无法区分需要 1 页和需要 6 页的新请求，而本方案使用实际分配计划。
同样，已经被其他请求持有的共享页不会再次减少空闲页数，空闲缓存页被重新持有则会减少空闲页数。
正确计算这一区别，比直接把提示词长度除以页大小更重要。

## 明确的边界

- 这是短期软预算，不是精确预知输出长度，也不是消除抢占的保证。
- 没有运行请求时不因软预留而拒绝唯一可运行的 Prefill，避免把进度停在原地。
- 只在尚未持有 KV 的请求首次分配或全量重算准入时检查；保留部分前缀的恢复路径不受此软预算约束。
- 不改写模型权重、Attention、采样算法或压缩策略。
- 不同优先级只影响预留对象，不能由此宣称 SLO 保证或通用公平性。
- 软预算可能把开销转移成等待与重复候选检查；在一次压力运行中出现了上万次检查，需与收益一起评估。
- 本轮 GPU 筛选关闭 Mooncake 和压缩，不代表验证了所有组合。
- 更多候选查找会改变前缀查找次数；不能仅凭缓存命中率变化宣称前缀缓存改进。

## 如何启用

在 WSL 中：

```bash
cd /mnt/d/nano-vllm-qos
KV_ADMISSION_LOOKAHEAD=32 bash scripts/run_nanovllm_wsl.sh
```

等价服务参数为 `--kv-admission-lookahead 32`。不要同时设置上一轮的 `MAX_NUM_ACTIVE_SEQS=8`，否则混合了两个实验变量。
默认值 0，不改变正常启动的行为。

可复现消融套件：

```bash
/home/xuhang/.venvs/nanovllm-qos/bin/python -m benchmarks.run_validation admission \
  --seed 20260906 --requests 600 --duration 300 --rates 2 --repeats 1 \
  --kv-admission-lookahead 32 --arrival-process uniform --max-inflight 512 \
  --output-dir benchmarks/results/my-page-admission
```

每个重复分别运行 H=0 和 H=32，重复轮次交替执行顺序；同一套代码、相同请求、相同模型配置，关闭调度追踪。
启动前检查服务端真实配置，每轮重启并预热；记录完整结果、失败请求和源文件哈希。
`--repeats 1` 仅是候选筛选，不提供可靠的波动范围；最终结论需要多轮、不同负载验证。

## 验证重点

首组筛选数据保存在 `benchmarks/results/kv-admission-20260906-screen/`。
两种策略各完成 601/601 请求，输出 Token 数均为 57,664，工作负载指纹一致，均未触发回收。
候选仅暂缓了 3 次准入检查，虽然该轮延迟更低，仍不足以把差异归因于页预留。
后续使用 3 请求/秒、每轮 361 请求、三轮交替对照，属于短时压力实验，不应称为长期稳定性验证。

所有请求结果都保留，不按是否满足 SLO 筛掉样本。最终对比使用各轮指标的均值与波动范围；
每轮每类约 180 个样本，P99 尾部样本尤其有限，不能把该百分位写成高置信度的生产结论。

交互请求的 SLO 为 TTFT 1,000 ms、TPOT 100 ms、E2E 10,000 ms；
批处理请求为 TTFT 10,000 ms、TPOT 500 ms、E2E 30,000 ms。
请求被判为满足 SLO 时，需要满足它所有配置的目标，而不是只满足其中一项。

新增单元测试覆盖物理页边界、即将完成的请求、Prefill 待执行状态、优先级、共享与空闲缓存页成本，以及大请求暂缓后的进度。
当前完整回归为 192 项通过。
服务指标 `kv_admission_deferred_checks` 是暂缓检查次数，不是不同请求的数量，也不是拒绝请求数。

实机结果必须同时报告两类请求的 TTFT/TPOT/E2E、回收和重算、失败率、输出长度及 SLO Goodput。
不能只挑回收减少这一项，更不能用到达速率受限的吞吐数据宣称引擎峰值能力。

## 三轮压力结果：2026-09-07

数据目录：`benchmarks/results/kv-admission-20260907-pressure/`。每种策略三轮，每轮 361 个请求，
固定 3 请求/秒、120 秒到达窗口、64 页 KV；H=0/H=32 交替运行，关闭追踪、压缩、Mooncake 和静态驻留上限。
共发出 2,166 请求，成功 2,165；候选第三轮的 `batch-120` 出现一次 `Errno 110` 连接超时。
服务日志没有对应异常栈，当前不能将其归因于调度策略或外部环境。失败样本没有删除或重跑替换。

以下为三轮指标均值，不是最优一轮：

| 指标 | H=0 | H=32 |
| --- | ---: | ---: |
| KV 回收事件/轮 | 17.33 | 12.67 |
| 重算 Token/轮 | 19,696.67 | 14,176.33 |
| 交互 TTFT P95 | 39.54 s | 41.72 s |
| 交互 E2E P95 | 42.16 s | 44.35 s |
| 批处理 E2E P95 | 63.44 s | 69.84 s |
| 输出吞吐 | 187.86 token/s | 181.68 token/s |
| SLO Goodput | 0.390 req/s | 0.417 req/s |

回收均值减少 26.9%、重算减少 28.0%，但交互与批处理尾延迟恶化，输出吞吐均值下降 3.3%。
Goodput 均值虽高 6.9%，95% Student-t 区间半宽分别约为 0.26 和 0.12 req/s，
且逐轮方向反转，不能据此宣称稳定收益。完整区间和逐轮数据见自动生成的 comparison 文件。
候选三轮共有 58,369 次暂缓检查，不是 58,369 个请求；反复查询的成本也属于策略代价。

结论：该启发式保留为默认关闭的实验候选，不作为简历加速成果，不替换默认策略。
下一步应先剖析模型执行、候选扫描与等待的时间占比，再决定改动，不能继续用降低回收次数代替服务质量目标。

## 压测后补齐的进度保障

额外的混合长度测试在 H=0 下也发现两条问题路径：

1. PALS 选中新请求但分配失败、且没有 Decode 请求时，没有继续执行已经分配 KV 的部分 Prefill，误报不可运行。
2. 最后一条 Decode 因页不足自我抢占后，缓存已经释放，却没有重新进入 Prefill 阶段，直接报错。

现在第一种情况会选择驻留 Prefill 继续执行，第二种情况允许重新调度一次；真正容量不足仍报错，不做无限重试。
新增定向回归和三种种子、两种策略的混合请求测试，验证完成与回收。
最新代码还通过 GPU 冒烟测试：4 页 KV、每步 128 Token、输入长度 513/769/257，
H=0 和 H=32 各完成 3 个请求，每个输出 4 Token，最后归还全部页。
结果在 `benchmarks/results/kv-admission-20260907-smoke.json`。

上述进度修复在六轮压力实验之后完成，所以旧性能数据不能当作修复后版本的完整性能复测。
GPU 冒烟只验证执行链路和完成情况，不验证模型质量或吞吐提升。
