# 多档五分钟在线消融结果

## 结果摘要（2026-09-08 核对）

18 轮全部结束，共 10,818 请求，10,817 成功。3 rps 的 legacy_cpu 第一轮有一个
batch 请求发生连接超时（Errno 110）；保留在原始记录及 offered SLO 分母中。
这不是完整原版 nano-vLLM 对比，而是当前引擎中默认设备上下文的单因素消融。

| 到达速率 | 基线交互 E2E P95 | scoped 交互 E2E P95 | 基线 / scoped 输出吞吐 |
| --- | ---: | ---: | ---: |
| 1 rps | 2.724 s | 2.225 s | 94.24 / 94.47 token/s |
| 2 rps | 2.749 s | 2.224 s | 188.43 / 188.98 token/s |
| 3 rps | 102.109 s | 24.167 s | 204.79 / 256.60 token/s |

表中为三轮统计量的均值，P95 不是合并所有请求后计算的分位数。
完整 Student-t 95% 区间见各档 comparison.md。3 rps 输出吞吐为
204.79 ± 48.35 与 256.60 ± 48.33 token/s；交互 E2E P95 为
102.11 ± 92.13 与 24.17 ± 62.16 秒，轮间波动很大，不据此宣称统计显著。

1、2 rps 下吞吐受输入速率限制，交互 P95 均值分别下降 18.3%、19.1%。
每分钟客户端未完成数未呈持续增长，最后到达后的客户端清空耗时为 4.37–5.85 秒。
这只描述本次有限测试窗口。

3 rps 下两种模式均持续积压。scoped 三轮最后到达时客户端未完成数为 168、61、53，
清空耗时为 68.87、24.12、20.94 秒；基线为 315、219、218 个和 173.11、97.98、101.91 秒。
scoped 平均完成吞吐只有 2.674 rps，仍低于输入的 3 rps。
虽然输出吞吐均值增加 25.3%，但不能写成稳定承载 3 rps。
scoped 交互 SLO 达标率均值为 52.6%，不能沿用短时实验的 98.2% 作为持续负载结论。

原始数据位于 `benchmarks/results/device-context-sustained-20260907/`，
其中 `progress-all.json` 包含全部 18 轮分时积压分析。连接超时并不证明后端同一时刻停止执行。
后续验证：WSL 完整回归 213 passed；Windows 控制面 203 passed、4 skipped，
跳过项为缺失 GPU 依赖或仅适用 Linux 的套接字测试，不计入通过数。

本实验延续短时在线消融，但不混用之前六轮数据。运行时代码、缓存和调度设置保持一致，
只比较推理线程保留 CPU 默认设备上下文的 `legacy_cpu` 与限定初始化作用域的 `scoped`。

## 预先固定的配置

- 负载：每秒 1、2、3 请求，均匀到达；每档两种模式、各三轮，共 18 次独立服务启动。
- 每轮至少覆盖 300 秒到达区间，分别为 301、601、901 请求，总计计划发出 10,818 请求。
- 顺序：每个负载档位按 legacy/scoped、scoped/legacy、legacy/scoped 交替。
- seed=20260908，区别于上一轮短时实验；seed 标识工作负载，不代表模型采样完全确定。
- 请求输出上限仍为 batch 128、interactive 64 Token，temperature=0.1，保留实际输出长度。
- 客户端最多 512 请求在途，每请求超时 300 秒，保留全部失败和客户端派发延迟。
- RTX 4060 8GB、Qwen3-0.6B、eager、PALS/Radix、64 页 KV、每步最多 8 请求。
- 关闭压缩、远端 KV、页预留、驻留上限与诊断追踪，指标汇总为 cached。
- 使用独立端口 8031，NCCL rendezvous 为 2333，结束后清理本实验进程组。

```bash
python -m benchmarks.run_validation device --seed 20260908 \
  --requests 2 --duration 300 --rates 1 2 3 --repeats 3 \
  --arrival-process uniform --max-inflight 512 --timeout 300 \
  --output-dir benchmarks/results/device-context-sustained-20260907
```

`--requests 2` 只设置最低请求数；实际数量由 duration 和 rate 计算。
均匀到达实现的第一个请求在一个间隔之后，最后到达时间约为 301/300.5/300.333 秒，
以原始记录为准。最后一个请求到达后继续等待完成或超时，不把到达区间当成总耗时。

## 新增的负载进展分析

```bash
python -m benchmarks.analyze_load_progress <trial.json> --output <new-progress.json>
```

脚本按实验时钟每分钟统计已计划到达、但客户端尚未结束等待的请求数，
并报告该到达队列样本的 queue P50/P95、失败数与最终清空时间。
最后一个不足一分钟的区间也保留；`arrival_window_s` 表示从实验时钟零点到最后计划到达的时间，
包括第一个请求之前的间隔。它不是最后到达减去最早到达。

这里不是 GPU 活跃请求数，也不等于服务端等待队列长度。客户端超时可能先于后端工作结束，
因此失败后的客户端计数下降不能解释为服务端压力消失。缺失终止时间时输出 null，不当作零。
请求排队指标缺失时记录可用样本数，不丢弃失败请求的计数。

## 判读规则

轻载时吞吐受输入速率限制，不以吞吐百分比宣称峰值加速。
接近容量时同时看分时积压、派发延迟、排队时间和清空耗时，避免只看整体均值。
过载时保留超时、未达标请求与输出长度；不能通过删掉失败样本美化 SLO。
三轮均值与 95% Student-t 区间一起报告，逐轮改善方向也保留。

即使五分钟内未见明显积压，也只能说明该有限窗口的现象，不是生产服务容量或长期可用性保证。
本轮不是与完整原版 nano-vLLM 对比，也不包含多机、其他模型或 CUDA Graph 的性能评估。

## 执行记录

运行时和压测脚本在实验期间保持不变。轻载 scoped 第二轮期间进行了约 8.5 秒的 Windows
CPU 控制面测试，它可能对主机调度产生干扰；保留该轮，不以重跑替换。结果不能描述为完全隔离的机器环境。
控制面检查发现 Windows 与 Linux 的 SO_REUSEADDR 行为不同，已在测试中标明 Linux 平台范围；
同时为导入 ModelRunner 的测试标明 GPU 依赖要求。只调整测试文件，未修改被测引擎或压测器。
