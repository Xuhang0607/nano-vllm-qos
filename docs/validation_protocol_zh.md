# 扩大评测与公平对照

本轮重点是补齐实机证据，并修正 Query-Aware 页预算在零匹配时不固定的问题。
已有 8 请求、3 次重复的压缩实验仍保留，但归类为探索性结果，不能直接推广为通用加速。

## 新增内容

- 质量矩阵：3 种文本长度、3 个证据位置、4 类任务、6 个随机样本，共 216 题。
  任务包括直接检索、问题改写、过期信息干扰、两段关联检索。答案随机生成，
  不从请求编号推导。它仍属于合成测试，不等同于真实业务质量评估。
  固定种子控制题目生成与到达轨迹；当前模型使用 temperature=0.1 随机采样，
  不保证重复运行逐 Token 相同，因此仍需多轮模型评估。
- 公平预算：Sink+Recent 保留 1+4 页；Query-Aware 保留 1+2+2 页。
  匹配得分为零时补选近期历史页，保持配置预算。相同页预算不意味着所有请求在
  每个时刻的 KV 使用量完全相同，因此还要检查实际丢弃量与压缩事件。
- 指纹校验：比较完整题目与答案的 SHA-256，并检查模型、输出上限、页大小、页池容量、
  压缩阈值；严格模式拒绝不同预算或缺失题目指纹的对照。
- 持续到达：支持固定间隔和固定种子的 Poisson 到达，同时打散两类请求。
  客户端限制并发连接，超限请求计为失败，不在隐藏线程队列里等待。
- 统计口径：记录发送延迟、客户端请求耗时及从计划到达时刻开始的耗时。
  `offered_slo_attainment` 把失败请求也放入分母；原 `slo_attainment` 为已评估成功请求口径。
  TTFT/TPOT 仍来自服务端事件计时，不等同于客户端流式逐 Token 测量。
- 证据提示：短于 300 秒、每类完成请求少于 200、P99 尾部样本不足、客户端发送拥塞，
  都会出现在结果或聚合报告中。阈值是项目评测规则，不代表达到阈值就充分可靠。

## 在 WSL 中运行

先停止自己启动的聊天服务，释放 GPU 和引擎的 NCCL 2333 端口。实验运行器不会终止
已有服务。它默认在 8031 端口运行独立进程组，结束时只清理自己创建的进程。

```bash
cd /mnt/d/nano-vllm-qos
source /home/xuhang/.venvs/nanovllm-qos/bin/activate

# 216 题 x 3 策略；默认相同 5 页保留预算。
python -m benchmarks.run_validation quality \
  --output-dir benchmarks/results/my-quality-run

# 三档请求到达率，每档两种策略各 3 轮。
# 每轮至少 500 请求，计划到达时长约为 300 秒或更长，另有排空时间。
python -m benchmarks.run_validation serving \
  --requests 500 --duration 300 --rates 0.5 1 2 --repeats 3 \
  --output-dir benchmarks/results/my-serving-run

# 正常自动页池容量对照，避免只在刻意缩小的页池上评价。
python -m benchmarks.run_validation serving \
  --kv-blocks 0 --rates 2 --repeats 3 \
  --output-dir benchmarks/results/my-normal-capacity-run
```

输出目录必须为空，避免覆盖已有实验。每轮保存 JSON、请求级 CSV、服务日志，
并记录启动配置、Git 状态和 Python 源文件摘要。端口空闲、显存可用是启动前提。
运行矩阵可能需要数十分钟到数小时；低到达率实验的计划时长为请求数除以到达率。

已有结果需要继续运行时，在原命令末尾加 `--resume`。运行器会校验参数与 Python
源文件摘要，跳过已保存的完整轮次；参数或源码不同会拒绝混合数据。
`status.json` 记录当前阶段、策略、轮次及完成/失败状态。

本轮独立质量验证使用种子 20260906。最初的性能实验发现客户端并发上限和服务端
事件等待问题后中止；修复后的重复性能实验使用以下命令：

```bash
python -m benchmarks.run_validation serving \
  --seed 20260906 --requests 600 --duration 300 \
  --rates 2 3 --repeats 3 --arrival-process uniform \
  --max-inflight 512 \
  --output-dir benchmarks/results/validation-20260905-repeated
```

其中每个策略在 2 req/s 下每轮 601 请求，在 3 req/s 下每轮 901 请求。
两组使用相同请求轨迹，并逐轮交替运行顺序；此命令使用固定间隔到达，
随机到达场景需另用 `--arrival-process poisson` 运行，不能混称为已覆盖。

`--lengths` 的单位是合成文本行数，不能写成 Token 长度；实际输入长度读取结果中的
`usage.prompt_tokens`。Poisson 到达的实际时长会波动，需检查报告中的实际值。

## 如何解读

1. 不压缩策略首先给出模型自身的任务准确率；先确认模型能完成任务，再评价压缩损失。
2. 同预算下比较 Query-Aware 和固定窗口；不要把“保留更多页”当成选页更好的证据。
3. 比较吞吐时同时检查完成数、失败数、实际输出 Token 数、客户端延迟、KV 压缩次数。
   模型允许 EOS 提前结束，不强制生成同样长度，输出长度变化需要一起报告。
4. 单次扩大请求数的实验仍不能替代多轮重复，也不能替代不同请求轨迹。
5. SLO 门槛在实验前固定。本运行器交互类使用 TTFT 1 秒、TPOT 100 毫秒、E2E 10 秒，
   是实验假设，不是行业统一标准。两组都 100% 达标时不能宣称调度质量得到改善。
6. 当前工作尚未验证多机 RDMA、长时间故障恢复或通用质量无损。不要写进简历。
