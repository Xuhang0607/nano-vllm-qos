# KV 抢占诊断

## 目标与边界

上一轮 cached 指标汇总模式的第三次 GPU 测试出现 13 次抢占，不能仅凭最终计数断言根因。
本轮增加调度事件追踪，用来还原首次页申请失败之前的请求和缓存状态。
追踪默认关闭，追踪本身不改变准入策略、抢占策略或 KV 压缩算法。
在捕获实机事件后，另增加默认关闭的驻留请求上限，用于验证准入过量这一假设。

## 实现

- `--scheduler-trace-path` 指定 JSONL 文件；文件必须不存在，避免覆盖或混合不同运行。
- 内存保留最近 512 个事件；跨页申请失败、回收计划和无可运行请求触发落盘，再记录后续 128 个事件。
- 最多触发 32 次，文件预算 16 MiB；重叠窗口按事件编号去重。到达上限或写入失败后关闭记录，不中断推理。
- 每个队列最多展开 64 个请求，同时保留完整队列计数，不能把截断的快照当成所有请求。
- 记录 Prefill 准入与阻塞、Decode 页不足、回收前后、完成和执行时间；请求快照包含优先级、PALS 预算、逻辑与物理缓存长度、页数和重算量。
- 不记录提示词、Token 值和模型输出。`age_ms` 是到达后的总时间，不是纯排队时长；`budget_ms` 是策略计算后的预算，不是原始 SLO。
- 不额外调用有副作用的前缀查找或容量检查，避免修改缓存命中计数及待分配状态。

这是诊断工具，不是零开销采样。开启时会复制元数据，触发时同步写文件。
带追踪的实验不能用于宣称吞吐提升；评测元数据标记 `scheduler_trace_enabled`，聚合工具拒绝混合不同追踪设置。
只有文件头表示未捕获事件，不表示调度已经最优。文件只保存有界事件窗口，不能用它代替整轮指标。

## 启动方法

在 WSL 中执行，输出路径每轮使用新名字：

```bash
cd /mnt/d/nano-vllm-qos
SCHEDULER_TRACE_PATH=/mnt/d/nano-vllm-qos/benchmarks/results/my-run.trace.jsonl \
  bash scripts/run_nanovllm_wsl.sh
```

独立的可复现实机诊断，不占用日常服务的 8020 端口：

```bash
/home/xuhang/.venvs/nanovllm-qos/bin/python -m benchmarks.run_validation trace \
  --seed 20260906 --requests 600 --duration 300 --rates 2 --repeats 1 \
  --arrival-process uniform --max-inflight 512 \
  --output-dir benchmarks/results/my-kv-trace
```

压缩关闭，PALS + Radix，64 页 KV，最多每步 8 条序列。诊断运行结束后自动关闭自己启动的服务。

## 确定性验证

小型 CPU 调度测试使用 4 页、每页 4 Token，两个不同的 8 Token 输入。
第一次 Prefill 用完 4 页，生成首 Token 后，两条序列长度变为 9；下一步 Decode 需要新页，因此触发抢占。
开启与关闭追踪的调度序列、完成指标和缓存计数完全一致。
这证明该路径可被观测，不等于证明上一轮 GPU 异常只有这一原因。

新增测试还覆盖窗口去重、事件数与字节上限、文件覆盖保护、磁盘写入失败及 CLI 参数。
当前完整回归为 169 项通过，包括驻留上限、取消释放名额、分块 Prefill 防止停滞、追踪数据隔离及远端恢复与 Decode 并存等测试。

## 实机捕获：2026-09-06

原始文件位于 `benchmarks/results/kv-trace-20260906-r2/`，601 个请求全部完成，压缩和 Mooncake 均关闭。
整轮指标记录了 5 次 KV 回收，失效 7,228 Token。事件文件在达到字节预算前捕获了 3 次跨页失败；不能把这 3 次当成整轮总数。

首次失败的时序：

1. 第 4169 步：运行队列 14 条，空闲 2 页，Decode 批次为 8 条。
2. 第 4170 步：继续准入一个请求，运行队列增至 15 条，空闲页变为 0；该 Prefill 执行 279 Token。
3. 第 4176 步：请求 303 的序列长度为 1,537，需要从 6 页扩展至 7 页，却没有空闲页。
4. 策略选择请求 310 作为受害者；这是预算排序的结果，不表示该请求是占用页面最多的请求。

这解释了本轮的第一条抢占路径：`max_num_seqs=8` 只约束每步批次，没有限制所有 KV 驻留请求的总数。
它不证明上一轮 13 次抢占具有完全相同的原因，也不排除 Prefill/Decode 干扰和执行估计误差的影响。

## 可消融的驻留上限

新增 `max_num_active_seqs`，默认 `None`，保留原行为。与每步批次上限分开配置：

```bash
MAX_NUM_ACTIVE_SEQS=8 bash scripts/run_nanovllm_wsl.sh
```

也可以使用服务参数 `--max-num-active-seqs 8` 或诊断套件参数 `--max-active-seqs 8`。
计数包括运行请求、有 KV 页的等待请求（分块 Prefill 或保留前缀）以及正在恢复 KV 的请求。
达到上限时，不再为尚未驻留的新请求分配 KV；已有部分 Prefill 仍可继续，避免被队首新请求阻塞。
完成、取消和释放全部 KV 后，其他请求可以获得名额。

这是请求数级准入控制，不是 Token 级页预留。长请求或页需求差异很大时仍可能发生抢占，不能承诺消除所有抢占。
它也可能推迟新到交互请求的首 Token，因此必须同时评估分类型 TTFT、E2E 和失败率。

## 候选策略的负面结果

另一个输出目录 `benchmarks/results/kv-trace-20260906-active8-r2/` 使用相同负载和 8 条驻留上限。
两轮均开启诊断，均完成 601/601 请求，各生成 57,664 Token；没有通过拒绝请求或缩短输出降低回收量。

| 指标 | 原准入 | 驻留上限 8 |
| --- | ---: | ---: |
| KV 回收事件 | 5 | 0 |
| 重算 Token | 5,948 | 0 |
| 交互 TTFT P95 | 304.72 ms | 4,850.22 ms |
| 交互 E2E P95 | 3,183.51 ms | 7,657.08 ms |
| 批处理 E2E P95 | 13,520.55 ms | 18,980.66 ms |
| SLO Goodput | 1.943 req/s | 1.213 req/s |

结论：减少抢占并不等于改善服务。固定驻留上限把部分压力转移到了准入等待，本轮交互延迟明显恶化，不应默认启用，也不能写成简历加速成果。
这只是各一次诊断性运行，不是最终同版本、多轮、关闭追踪的性能消融；基线在加入候选选项之前运行，两个目录分别保存源文件校验清单。
基线事件文件还触发了大小上限，因此两轮追踪成本也不相同。表格用于记录观察和否定过早的优化结论，不用于计算可推广的提速比例。

## 额外的正确性修复

调度器从 `running` 队列取出可执行序列后，如果同时存在远端恢复，旧代码会因为临时队列为空而提前返回空批次，丢失已经选中的 Decode。
条件已改为检查 `scheduled_seqs` 是否为空，保证有可执行批次时继续执行，没有时才等待远端恢复。
新增回归在修复前失败、修复后通过。这是 CPU 调度状态测试，并非本轮完成了 Mooncake 硬件传输验证；两轮 GPU 诊断都关闭了 Mooncake。

## 后续决策

先对照实机追踪的首次失败时刻，检查准入时剩余页、在途 Decode 的跨页需求、Prefill 执行时长和重复抢占对象。
下一轮考虑结合实际页需求与请求优先级的准入预算，而不是仅限制驻留数量；同时检查 Prefill 是否阻塞 Decode。
应在冻结实现、关闭追踪后，多轮对照原策略，并明确交互与批处理的权衡，再决定是否更改默认值。
不要把更多测试请求拒绝、普通请求延迟增加或更短输出，误报为整体优化。

WSL 已检测到 Nsight Systems，进程树 CPU profiling 环境检查通过；系统级采样检查未通过。
本轮尚未据此声称完成 GPU timeline 分析，也不更改系统采样权限。
